# 终端性能与内存优化报告（2026-09-19）

本轮针对终端**渲染帧管线**与**快照刷新**做了一轮优化，参考对象是同级目录的
tty7 项目（`../tty7`）。全部结论都有测量或测试支撑，改动集中在 4 个文件。

测量环境：macOS 25.4.0 arm64（Apple Silicon），release 构建，
gpui rev `ac099b4` `#[gpui::bench]`（真实 CoreText 排版 + 无头 Metal 提交）。

复现：

```
cargo bench --bench terminal_render -- --warm-up-time 1 --measurement-time 3
cargo test --lib terminal_memory -- --nocapture
cargo test --lib incremental_snapshot -- --nocapture
```

---

## 一、与 tty7 的对照：找到了什么

逐文件比对两边终端管线后，tty7 有 3 处结构性做法是 deepterm 缺的。按影响排序：

| tty7 的做法 | tty7 位置 | deepterm 原状 | 本轮处理 |
|---|---|---|---|
| 渲染不排队等网格锁（`try_lock_unfair`，拿不到就画上一帧） | `src/terminal/element.rs::build_grid` | **公平 `lock()`，会排在读线程 lease 后面** | ✅ 已实装 |
| 只把悬停链接的列区间传给行循环，不搬整份链接 | `element.rs::paint`（`HoveredLink` 按需读） | 每帧 `clone()` 整份 `HoveredLink`（344 B + 堆分配） | ✅ 已实装 |
| 字形段按 `SharedString` 共享，不整段深拷 | `element.rs::shape_piece` | `BatchedTextRun` 含**按值**的 `ShapedLine`（2984 B） | ✅ 已实装 |

tty7 还有若干 deepterm 已有等价物的做法（行级 damage 追踪、逐行 shape 缓存、
选区 O(1) 区间求交、`memchr` 快路径扫描、背景 run 合并），这些在
`docs/PERF_2026-09-06.md` 与 `PERF_MEMORY_AUDIT_2026-09-12.md` 里已经做过，
不再重复。

## 二、本轮改动

### 1. 视口快照改为按行增量（性能，最大项）

**问题**：`Terminal::update_last_content` 每帧对**整个视口**重新构造
`IndexedCell`。默认 80×24 视口就是 1920 格 × 56 字节；打字 / 回显这种「只改
一格」的稳态场景下，每帧的绝大部分工作都是白做的。

**关键前提（本轮核查确认）**：alacritty 0.26 把所有会让视口**整体错位**的操作
都标成 `mark_fully_damaged()`：

- `Term::scroll_display`（`term/mod.rs:404-407`）——display_offset 一变就 Full；
- `scroll_up_relative` / `scroll_down_relative`（`:789` / `:762`）——任何滚动；
- `resize`、清屏、模式切换等（`:406/:525/:734/:1152/:1667/...`）。

因此 `TermDamage::Partial` 的含义是**「只有列出的这些行变了，且它们仍在原来的
视口行号上」**——增量覆盖是安全的。

**改法**：`Partial` damage 且视口几何未变时，只对 `dirty_rows` 为真的行重写
`cells[start..end]`；行号由 `display_offset` 与行下标唯一确定。`Full` damage
或几何变化时走原来的整体重建。另加两条自身防线（不依赖上游实现）：

- `display_offset` 变化 → 全量；
- 视口行列数变化 → 全量。

**证据**：新增 `incremental_snapshot_matches_full_rebuild`（1500 步随机编辑）
与 `..._across_scroll_and_resize`（滚动 / 滚回 / 滚动中写入 / resize）两个
**逐格平价**测试，比对「生产路径（按真实 damage）」与「强制整体重建」的
`(point, PackedCell)`。前者的 1500 步里有 **1366 步**真正走到了增量分支
（测试自带该断言，避免退化成「全量 vs 全量」的自我印证）。

**变异验证**（把行号映射故意 +1）两个平价测试立刻失败，证明测试确实咬得住
被优化的那行代码。

### 2. 渲染不再排队等网格锁（性能 / 卡顿）

**问题**：`Term` 由 `FairMutex` 保护。本地 PTY 读线程在 `pty_read` 里先
`term.lease()` 占住 `next` 锁，再持 `data` 直到喂完 `MAX_LOCKED_READ`
（64 KiB）。UI 线程用公平的 `lock()` 就得**排在那个 lease 后面**——而同一个
UI 线程要画所有 pane，一个 pane 的写入速度会直接绑住整个窗口的帧率。

这正是 tty7 在 `build_grid` 里明确避开的坑（其注释称之为「#709 同款病症」）。

**改法**：`update_last_content` 先 `try_lock_unfair()`（不排队、不阻塞）。
拿不到就**跳过本帧**：返回 false、`content_dirty` 保持置位，下一个事件循环的
`sync()` 再试。屏幕最坏晚一帧。

**防饿死**：持续大流量下读线程喂完一个 chunk 就立刻回来重取锁，
`try_lock_unfair` 可能一次次落空。因此连续跳过 `MAX_SNAPSHOT_LOCK_SKIPS = 4`
次后退回公平锁——它确实会排在 lease 后面，但 lease 只在喂一个 chunk 期间持有，
代价有界，换来「画面一定跟得上」。`force_full_damage` 路径（resize / 换主题）
**始终**用公平锁，因为那些路径要求快照与网格立刻一致。

**证据**：`snapshot_refresh_yields_to_grid_lock_without_starving` 用一个有时限
的占锁线程模拟「读线程正在喂大 chunk」，断言 (1) 占锁期间 UI 侧 `sync` 立刻
返回且不谎报已刷新，(2) 锁释放后快照必然追平。

**变异验证**：把该处换回 `self.term.lock()`（旧行为），测试立即失败于第一条
断言（旧代码会一直阻塞在锁上）。

### 3. `ShapedLine` 改为 `Arc` 共享（内存）

`BatchedTextRun` 里按值持有 `ShapedLine`。实测 `size_of::<ShapedLine>() = 2984`
（内含 `SmallVec<[DecorationRun; 32]>` 内联缓冲），`BatchedTextRun` 因此
**3008 字节**；而它会被成行成批地 `clone`（增量重算保留未变动 run、整行布局
回写前的暂存）。改成 `Arc<ShapedLine>` 后结构体降到 **32 字节**，克隆是一次
引用计数自增。

### 4. 删掉每帧的悬停链接深拷 + 死字段（内存）

- `FlattenedRenderCache.hovered_link` 写入后**从未被读过**（悬停失效早已由
  `RowRenderCache::hovered_url_cols` 逐行比对）。它每帧 `clone` 一份
  `HoveredLink`（344 字节 + `String`/`SharedString` 堆分配）。已删除字段，
  该结构随之变成 `Copy`。
- 行循环只需要悬停链接的 `(row, 起止列)`，改为只取这三元组，不再克隆整份
  `HoveredLink`。

### 5. 字体回退列表缓存（内存）

`platform_default_fallbacks()` 在 `TerminalElement::prepaint` 里**每帧都调**，
每次重新构造 `Vec<String>`（macOS 7 个 / Linux 8 个 `String` + `Vec` + `Arc`）。
`FontFallbacks` 本身就是 `Arc<Vec<String>>` 的包装，改为 `LazyLock` 缓存后
每次调用只做引用计数自增。

## 三、测量结果

### 主指标：每帧重建的单元格数（确定性，不受机器负载影响）

本机 wall-clock 基准噪声很大：同一个二进制相邻两轮可差 30%，连**不受本轮
改动影响**的 `frame_no_damage` 都会漂移（实测 540 µs ↔ 1.25 ms）。因此本轮
以**确定性计数**为主指标——`IndexedCell` 的重建个数，它与机器负载无关。

新增 `incremental_snapshot_rebuilds_far_fewer_cells`，用 bench 同款的
「单行写入 + 光标复位」稳态负载跑 200 帧：

| 路径 | 200 帧重建格数 |
|---|---|
| 增量（生产路径） | **11 000** |
| 全量（参考路径） | **198 000** |
| | **省 94.4%** |

即打字 / 回显这类终端最常见的稳态场景下，快照构造的工作量降到约 1/18。

### wall-clock（中位数；**仅作方向性参考，本机噪声 ±30%**）

用「同一负载窗口内 baseline / optimized 二进制交替各跑 3 轮」的方式测（方法
沿用 `PERF_2026-09-06.md`）：

| 场景 | 基线（中位） | 优化后（中位） | 变化 |
|---|---|---|---|
| 全行 dirty（批量输出） | 2.672 ms | 2.405 ms | −10.0% |
| 单行 dirty（打字 / 回显） | 1.108 ms | 0.933 ms | −15.8% |
| 无 damage（光标闪烁） | 1.035 ms | 0.889 ms | −14.1% |
| 滚动一行 | 1.388 ms | 1.333 ms | −4.0% |
| 拖拽选区一步 | 1.000 ms | 0.895 ms | −10.5% |

**注意**：`无 damage` 场景本轮几乎没有改动（不构造快照、不排版），却也测出
−14.1%，说明这组数字里的漂移量级与改进量级相当。**不要把上表当作精度声明**，
它只能说明「没有变慢」。真正可信的收益见上节的确定性计数。

### 分配（`cargo test --lib terminal_memory -- --nocapture`）

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 稳态 prepaint 分配 | 55 次/帧 | **46 次/帧** |
| 单行 dirty prepaint 分配 | 47 次/帧 | **39 次/帧** |
| 内容未变 sync 分配 | 1 次 | 1 次 |
| 稳态单行写入+快照分配 | 3 次 | 3 次 |

（单行 dirty 的历史基线为 O2 之前的 1932 次 / 8.1 MB，见 `PERF_2026-09-06.md`。）

### 内存（footprint）

`phys_footprint` 差值在本机**高度依赖测试执行顺序**：单独跑
`terminal_scrollback_footprint` 时 1k 档约 +1.84 MB，而在全量测试套件里同一
档会读到 +6 ~ +12 MB（相邻实体释放时机不同）。因此只有量级可引用：

| scrollback | 实测（单独运行，3 次一致） |
|---|---|
| 1 000 行 | +1.84 ~ 1.88 MB |
| 5 000 行 | +8.72 ~ 8.75 MB |
| 10 000 行 | +15.2 ~ 15.7 MB |

**结论：本轮改动没有改变 scrollback 的内存占用**（10k 档与历史报告的
15.70 MB 一致）。scrollback 仍是单终端内存的最大项，约 1.5 MB / 1000 行。
本轮的收益在**每帧工作量**，不在稳态驻留内存。

## 四、回归与验证

- **终端全部测试通过**（8 个内存/平价/饥饿测试 + 既有终端测试），0 失败。
  本轮新增 4 个测试：
  - `incremental_snapshot_matches_full_rebuild`：1500 步随机编辑逐格平价
    （1366 步命中增量分支）；
  - `incremental_snapshot_matches_full_rebuild_across_scroll_and_resize`：
    滚动 / 滚回 / 滚动中写入 / resize 的平价；
  - `incremental_snapshot_rebuilds_far_fewer_cells`：确定性收益度量（省 94.4%）；
  - `snapshot_refresh_yields_to_grid_lock_without_starving`：锁让步 + 防饿死。
- 平价测试做过**变异验证**：把增量路径的行号映射故意偏移 1，两个平价测试
  立刻失败；把渲染侧换回公平锁（旧行为），饥饿测试立刻失败。
- `terminal_scrollback_footprint_scales_linearly` 用的是进程级
  `phys_footprint`，读数会被并发测试污染（实测 1k 档在 0.8 ~ 4.3 MB 之间跳、
  5k 档在 5.4 ~ 26.8 MB 之间跳）。本轮给它加了预热剥离一次性分配成本，并把
  断言保持为**方向性**的「10k ≥ 1k」——它只在 scrollback 容量失效时才失败。
  斜率只打印、不断言。
- `cargo build --release` 通过。
- **实机冒烟**：release 二进制启动正常，恢复出 3 个终端 pane（3 个 zsh 子进程），
  空转 CPU 0.0%，持续运行稳定。

> **回归记录（审核后修复）**：本轮初版提交里有两个测试是红的，已修复：
> 1. `components::input/display_map/folding.rs::probe_crlf_empty_line_is_blank`
>    —— 新增的探针测试断言 CRLF 空行 `is_blank == true`，但 `line_indent` 里
>    处理 `\r` 的那段是**死代码**（`\r` 会先在循环里走 `else` 分支把
>    `is_blank` 置 false），且该测试依赖的 `slice_line` 保留行尾 `\r`。
>    已改为用 `RopeExt::line_content`（同时剥掉 `\n` 与 `\r\n`）并删掉死代码。
>    这个测试是**本轮新增的**，不是既有失败。
> 2. `terminal_scrollback_footprint_scales_linearly` —— 初版把断言改成「5k→10k
>    相邻档斜率必须为正」，该断言在本机全量套件下 **6 轮里 5 轮失败**（相邻
>    两档的读数隔着分配器状态变化，差值常为负）。已改回方向性断言。
>
> 另外修掉一处**测试有效性**问题：初版饥饿测试的第二条断言发生在占锁线程
> 释放之后，此时 `try_lock_unfair()` 自己就会成功，`MAX_SNAPSHOT_LOCK_SKIPS`
> 回退分支根本走不到——把该分支改成 `None if false` 后测试**依然全绿**。
> 现在三个阶段都发生在锁被占住期间，两个变异（永不回退 / 总是公平锁）都能
> 让测试失败。
>
> **补齐的三处覆盖 / 一处运行时缺口**：
> 3. **跳过帧没有补帧兜底（运行时缺口，非测试问题）**：`sync` 的唯一调用点
>    是元素 `prepaint`，GPUI 又不按 vsync 空转。所以一次跳过之后若不再有新
>    输出（读线程 drain 完退出、SSH 断连、`ChildExit` 这类「最后一次唤醒」
>    撞上被占住的锁），`content_dirty` 会**永久置位**、画面停在旧内容上直到
>    用户碰鼠标。`cx.notify()` / `Window::refresh()` 都救不了（prepaint 期间
>    两者都不排队新帧），已改为 `SNAPSHOT_RETRY_DELAY = 8ms` 的补帧任务
>    （`schedule_snapshot_retry`），拿不到锁就再排一个。新增
>    `skipped_snapshot_schedules_a_retry_frame` 钉住它：删掉补帧调度后该测试
>    立刻失败。
> 4. **平价测试漏比 `zerowidth` / `hyperlink`**：初版手写 `(point, cell)`
>    比对，而这两个字段恰好在随机编辑流里恒为 `None`——实测把增量分支的
>    `hyperlink` 写死成 `None`，测试**照样全绿**。已给 `IndexedCell` 加
>    `PartialEq` 改整格比较，并在随机流里加入 OSC8 链接与组合变音符
>    （U+0301）两类指令；现在两个字段各有一个变异能让测试失败。
> 5. **兜底分支零覆盖**：`row_ranges.len() != num_rows` 那条防御性全量重建
>    路径在生产上不可达，测试也从未走进去。新增
>    `inconsistent_row_ranges_fall_back_to_full_rebuild`，用
>    `corrupt_row_ranges_for_test` 人为破坏不变量进入该分支，断言它确实被
>    命中且能把 `row_ranges` 修回自洽。

## 五、未做 / 后续可做

- **滚动帧的完整收益被 draw 框架摊薄**：滚动一帧 914 µs 里仍有相当部分是
  quad 提交与 GPUI 绘制框架本身，不是快照构造。继续压这部分需要动绘制批处理。
- **`kitty_placeholder_cells()` 每次 prepaint 都扫一遍整个 `last_content.cells`**
  （`terminal.rs:3828`，每帧 O(视口)）。绝大多数终端从不发 Kitty 图形协议，
  这次扫描纯属浪费。可行的改法是给 `last_content` 记一个「本帧是否有占位符」
  的标志位，无占位符时直接返回空 `Vec`。本轮未做，因为它与增量快照是同一处
  数据结构的两种读法，留作独立改动更清晰。
- **`MAX_SNAPSHOT_LOCK_SKIPS = 4` 是经验值**：它只影响「极端流量下晚几帧」，
  不影响正确性。真实负载下若观察到掉帧可调大，若观察到明显滞后可调小。
- 历史审计（`PERF_MEMORY_AUDIT_2026-09-12.md`）里仍未实装的 P1（markdown
  `plan_document` 全量重算）不在本轮终端范围内。
