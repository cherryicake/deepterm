## 二、终端行缓存：增量 run 更新线性化 + 去掉整行克隆

### 2.1 根因

`src/terminal_view/terminal_element.rs` 的 `try_update_runs_in_range` 在重排
脏区间前，需要把区间扩展到「完整 run 段」。旧实现是固定点循环：

```text
loop {
    for run in cached_runs {           // 每次从头扫描
        if run 与当前区间相邻 { 扩展区间; changed = true; }
    }
    if !changed { break; }
}
```

`cached_runs` 按 `start_col` 升序，但左侧扩展只能发生在右侧 run 被访问之后。
若一行有 N 个相邻的彩色 run，而脏区在最右侧，则**每轮只能向左扩一个 run**，
最坏 O(N²)。这正对应彩色进度条、逐单元格着色的构建输出等长行。

同一路径还有一处与算法无关的开销：

```rust
let cached_entry = row_cache.layout.clone();   // 克隆 Vec<BatchedTextRun> + Vec<DecorationSpan>
```

即使随后立即整体替换缓存，也要先付一次整行 layout 的堆拷贝。

### 2.2 改动

- 利用「`cached_runs` 已按 `start_col` 排序」的不变量，先用
  `partition_point` 定位区间右端，再用两个只前进/后退的游标
  （`lo` / `hi`）把相邻 run 段一次性扩展完；每个 run 至多访问一次，
  总复杂度 O(runs)。
- 增加 `debug_assert!` 明确并保护排序不变量。
- `row_cache.layout.take()` 取代 `clone()`，直接消费旧条目；
  合并时用 `with_capacity` + `extend_from_slice(prefix/suffix)`，
  不再把未受影响的 run 过滤进新 `Vec`。
- 调用点删除多余的 `let mut entry = cached_entry` 中间绑定。

### 2.3 复验

`foreground allocations per iteration`（最小值，越低越好）：

| 场景 | 改动前 | 改动后 #1 | 改动后 #2 | 说明 |
|---|---:|---:|---:|---|
| `frame_all_rows_dirty` | 2145 | 2100 | **2089** | 全行脏，-2.6% |
| `frame_scroll_one_line` | 1896 | 1851 | **1851** | -2.4% |
| `frame_single_row_dirty` | 134.4 | 133.4 | **133.6** | -0.8 |
| `frame_no_damage`（未改动，对照） | 129.37 | 129.19 | **129.19** | 不变 |
| `frame_selection_drag`（未改动，对照） | 130.42 | 130.35 | **130.65** | 不变 |

两个**未走新增/修改路径**的对照场景读数保持不变，说明差异来自改动本身，
而不是全局环境漂移。减少的分配数约为视口行数（每脏行少一次 layout 克隆）。

`foreground instructions` 最小值在改动前后差异 < 0.4%（如
`frame_all_rows_dirty` 15.875M → 15.832M），符合预期：本场景里排版/整形
仍占主导，本次改动移除的是二次扫描与堆拷贝，不是整形本身。

墙钟时间（mean）在三次运行中从 1.36 ms 漂移到 2.58 ms 再回落，且未改动
场景同步漂移，**不采信**。

### 2.4 正确性验证

- `DEEPTERM_VALIDATE_ROW_CACHE=1` + debug profile 跑
  `frame_all_rows_dirty` 100 帧：每行缓存都与「全量重排」逐项比对
  （runs / box cells / backgrounds / selection spans），无断言失败。
- `cargo test` 全量通过（见第四节）。

## 三、Markdown：`RowPlan.visible` 改 `SharedString`

### 3.1 根因

`RowPlan` 是每行规划结果，`visible: String`。渲染时每个可见行都要：

```rust
SharedString::from(plan.visible.clone())
```

即每帧每行复制一次可见文本。改前每个可见行至少产生 1 次堆分配。

### 3.2 改动

- `RowPlan.visible` 改为 `gpui::SharedString`（`layout.rs`）。
- `Builder::finish` 在规划结束时把 `String` 转成 `SharedString`（一次）。
- `strip_plan_prefix`（`reveal.rs`）继续用 `.into()` 生成切片后的字符串。
- 渲染路径（`view.rs` 5 处）改为 `plan.visible.clone()`，只做引用计数递增。
- 测试辅助函数相应 `.to_string()`。

### 3.3 复验

`foreground allocations` 最小值（每帧）：

| 场景 | 1k 行 | 5k 行 | 20k 行 |
|---|---:|---:|---:|
| 空转 `frame_blink` · 前 | 2639 | 2640 | 2640 |
| 空转 `frame_blink` · 后 | **2613** | **2615** | **2614** |
| 滚动 `frame_scroll` · 前 | 3054 | 3055 | 3055 |
| 滚动 `frame_scroll` · 后 | **3024** | **3025** | **3025** |
| 单字符 `frame_type` · 前 | 3362 | 5038 | 11312 |
| 单字符 `frame_type` · 后 | **3336** | **5012** | **11286** |

三档文档规模下减少量完全一致（**26~30 次/帧**），且与视口行数同量级，
说明收益来自每个可见行少一次字符串分配，而不是文档规模相关的路径；
斜率也保持不变（空转仍与文档规模无关）。

`foreground instructions` 最小值同样基本不变（如空转 1k 行
7.846M → 7.833M），说明这是**分配器压力**优化，而不是指令数优化。

墙钟时间（mean）在同一轮 before/after 中：滚动三档下降 10.9% / 17.0% /
15.6%，单字符三档下降 11.3% / 12.3% / 13.1%；但空转 5k 行出现 +10.6%
回退，且指令数未下降。结合当轮机器负载漂移，这组墙钟数字**不能全部归因于
本次改动**，仅记录现象，不作为收益承诺。
